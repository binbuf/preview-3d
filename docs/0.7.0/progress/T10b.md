# T10b - 3MF best-effort compatibility

## Reusable facts

- Required-extension policy lives in
  `import-worker/src/ThreeMfDisplayProperties.cpp` (`CheckRequiredExtensions`).
  It runs in the product-owned XML pre-scan before lib3mf.
  - Supported: Core, Materials, Production, Beam, Ball.
  - Terminal geometry replacements: Slice `1001`, Volumetric `1002`,
    Implicit `1003`, Secure Content `1004`. The failed ID is stored in
    `ThreeMfDisplayCatalog::requiredExtensionFailureId`.
  - Every other required namespace: `Ignored` record `1000` and continue.
  - An undeclared required prefix stays `UnsupportedRequiredFeature` (malformed
    XML usage, historical behavior).
- `ThreeMfDisplayCatalog` now owns a `model_core::CompatibilityReportBuilder`.
  `PropertyCatalog::MergeCompatibility` folds those records into the generation
  report; `BoundedChunkWriter::AddCompatibilityReport` emits the one
  `CompatibilityReport` chunk before `Complete()`.
- Pure per-corner planner: `import-worker/src/ThreeMfMaterialPlan.h`
  (`PlanThreeMfTriangleMaterials`). Choices: `Uniform`, `Split`, `Dominant`.
  Dominant corner is the first most-frequent grouping, tie-break lowest index.
- Split rule in `EmitMesh`: centroid fan `(C, Pi, Pi+1)` for each corner when
  `triangleCount * 3` stays within `kTierBTriangleLimit - totalTriangles`.
  Each piece forces the corner's texture/sampler/layer/mix grouping; positions,
  winding and bounds are unchanged, authored corner UVs are retained.
  If a piece material/image cannot be produced, the whole triangle degrades to
  the dominant corner. No new limits were introduced (existing Tier-B triangle
  and material caps).
- Records added in `shared/model-core/include/model_core/Compatibility.h`:
  `1000` unknown required, `1001` slice, `1002` volumetric, `1003` implicit,
  `1004` secure content, `1010` per-corner split, `1011` per-corner dominant,
  `1012` slicer-private object type, `1013` unsupported object type,
  `1014` translucent display property, `1015` unsupported display property,
  `1016` multiple texture layers, `1017` texture decode fallback,
  `1018` multiple PBR layers.
- lib3mf 2.5 binds one property resource (`pid`) to a triangle. A compliant file
  cannot expose different texture identities across `p1/p2/p3`, so the split
  path is defensive. The real fixture exercises per-corner UVs; the planner
  unit test covers differing groupings and the dominant fallback.
- Tests are `[3mf-compat]` in `tests/import-isolation/ThreeMfSpikeTests.cpp`.
  Helpers: `CompatibilityRecords(result)` and `HasCompatibilityRecord(...)`.
  `CoreBoxVariant` now accepts `requiredAttribute`/`requiredNamespace`, and
  its `privateMetadata` option declares PrusaSlicer/Bambu private namespaces.

## Gotchas

- `production-boxes.3mf.base64` deliberately requires the Slice namespace and
  its visible geometry is slice data. It must remain a typed
  `UnsupportedRequiredFeature`; do not "fix" that fixture.
- `static-production.3mf.base64` carries the same Slice namespace but does not
  declare it required, so it still opens.
- A 3MF texture part needs both the `[Content_Types].xml` PNG default and a
  `3D/_rels/3dmodel.model.rels` relationship of type `.../3dtexture`; without the
  relationship lib3mf rejects the package as malformed.
- A real PNG is required for the texture fixture; a fake PNG header makes WIC
  fall back and is still not a valid package texture for lib3mf.
- `std::span<PropertySample, 3>` is fine inside `MaterialFor`, but a raw
  `PropertySample[3]` function parameter decays to a pointer and cannot be used
  in a range-for.

## Follow-ups

- If a future 3MF producer/library exposes per-corner property resources, add a
  real grouping-variation fixture; the current split path is already bounded
  and deterministic.
- Out of scope remains plate grouping/print settings, Slice/Secure
  Content/Volumetric/Implicit/toolpath semantics, and new geometry types.
- Do not use Assimp's 3MF importer as a fallback (T10 excludes 3MF); revisit only
  if the lib3mf policy proves insufficient.
