# 0019 — Provider COM host harness shape and the golden-fixture registry

## Status
accepted

## Context
T17 must give every later family adapter (T21–T34) one repeatable harness that
activates the provider through the real Shell COM sequence, compares golden
images, drives parallel apartments and samples GDI/User/private-byte leaks across
repeated load/unload. The frozen name is `Tests.ProviderHost.exe`
(T05/ADR-0010); ADR-0013 and ADR-0015 say it activates via
`DllGetClassObject` rather than linking (the exports are `PRIVATE`). At T17 the
`FamilyAdapterRegistry` still returns `nullptr` for every family, so no COM call
can render a bitmap yet, but the golden comparator and fixture registry must be
proven now — and the oracle for "did the pipeline work" must not be a second copy
of the pipeline.

## Decision
- **Two complementary layers, one executable.** `Tests.ProviderHost.exe`:
  1. loads the built `Preview3DThumbnailProvider.dll` and runs the Shell sequence
     (`DllGetClassObject` → `IClassFactory::CreateInstance` →
     `IInitializeWithStream` → `IThumbnailProvider::GetThumbnail`) per frozen
     CLSID, asserting either a real `S_OK`/`WTSAT_ARGB` bitmap or the
     `ERROR_NOT_SUPPORTED` null-bitmap fallback, then `DllCanUnloadNow == S_OK`;
  2. compiles the shipped `ThumbnailPipeline.cpp`, `GeometrySampler.cpp`,
     `CpuRasterizer.cpp`, `RasterBitmap.cpp` and `FamilyAdapterRegistry.cpp` and
     renders registered fixtures through the real orchestration so a golden can
     be compared before the first adapter lands.
- **A build-time fixture registry** (`tests/provider-host/FixtureRegistry.{h,cpp}`)
  holds one `GoldenFixture` per family task: family, small committed source
  bytes, golden path, tolerance and `cx`. `FixtureRegistry.cpp` is additive.
- **A single tolerant comparator** (`tests/provider-host/GoldenImage.h`): mean
  absolute error per channel plus a max-outlier guard (defaults
  `meanAbs <= 2.0`, `maxAbs <= 48`), the metric `docs/design/testing-strategy.md`
  already fixes and T15's rasterizer goldens use. Goldens are PAM, matching the
  T15 container, and regenerated by the hidden `[write-host-goldens]` case.
- **A `Family::Unknown` placeholder adapter** emits the same fixed UV sphere as
  the T15 golden, so the harness — adapter → sampler → rasterizer → comparator —
  is exercised end to end today. Family tasks swap in their routed adapter by
  registering a fixture and linking the adapter source into the host; the
  platform is then tested before the Shell is.
- **Parallel and leak layers** use the real COM objects (multiple STA
  apartments, repeated `LoadLibrary`/use/`FreeLibrary`) and sample GDI/USER via
  `GetGuiResources`, private bytes via `GetProcessMemoryInfo`, and thread count
  via a Toolhelp snapshot, failing on growth beyond fixed tolerances.
- **Rejected:** linking the DLL for the golden path (the exports are `PRIVATE`
  and this is not how the Shell activates it); a second pipeline implementation
  as the oracle (a copy drifts); a surrogate run (T03/T44 own that, and T17 must
  stay CI-runnable).

## Consequences
- The host links only the shipped provider core plus Catch2 and the Windows
  system libraries (`ole32`, `user32`, `gdi32`, `psapi`); it adds no product
  dependency and changes no DLL source.
- A family task's golden now has an exact, documented workflow
  (`tests/provider-host/README.md`): link the adapter, register the fixture,
  regenerate the committed PAM, verify both configurations. T21 is the first
  consumer.
- `[host][com]` is written to accept either the fallback (today) or a real
  bitmap (once a family lands), so it stays valid as the registry fills in and
  the Shell path becomes observable without editing the test.
- Surrogate-only checks (real `DllHost.exe`, DPI, clean-machine install) remain
  T44; this harness proves the in-process contract those depend on.
